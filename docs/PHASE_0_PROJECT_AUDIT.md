# 阶段 0：项目审计与开发基线

## 1. 阶段目标

在继续开发前，准确掌握现有后端代码、数据库、接口和运行方式，建立可信的项目基线。当前后端已有部分代码，前端尚未开始；本阶段不以新增功能数量作为目标，而是降低后续返工风险。

## 2. 产品定位与范围原则

本网站的首要目的，是**记录并展示个人学习过程、技术实践、生活兴趣与爱好分享**。首版优先服务站点所有者本人，访客主要以阅读和浏览为主。

首版不默认建设多用户社区，不把开放注册、用户投稿、评论、点赞、关注、私信等作为必需功能。若现有后端已经实现用户认证，应审计其价值和维护成本，再决定保留为管理员登录、简化或暂时不启用；不要为了沿用既有接口而扩大产品范围。

## 3. 审计范围

-   仓库目录、Git 状态、Maven 依赖、Java 版本和构建方式。
-   Spring Boot 启动配置、环境变量、日志和异常处理。
-   Entity、Mapper、Service、Controller 的分层和实现程度。
-   MySQL DDL、初始化数据、索引、逻辑删除及实际数据关系。
-   Redis 的实际用途；若当前功能不需要，不应仅因配置中出现就强制依赖。
-   `API_SPEC.md` 与实际接口的差异。
-   `CLAUDE.md` 与实际代码规范的差异。
-   前端尚未开始的事实，以及容器化运行的可行性。
-   密钥、数据库密码、API Key 等敏感信息是否误入代码或 Git。

## 4. 执行步骤

1.  获取完整项目 ZIP 或仓库，排除 `target`、`.git`、`node_modules`
    等非必要内容。
2.  检查 `pom.xml`、配置文件、SQL 脚本、测试代码和启动入口。
3.  在不破坏现有数据的前提下尝试构建和启动；记录环境要求和错误。
4.  列出每个模块的真实状态：已验证完成、部分实现、未实现、存在缺陷、暂无法验证。
5.  对照 API 文档核查路径、HTTP 方法、参数、响应、权限和错误处理。
6.  将问题按
    P0（阻断/安全）、P1（核心功能）、P2（体验/维护）、P3（未来扩展）排序。
7.  明确首版范围及暂缓事项，并估算后续阶段的任务。

## 5. 交付物

-   `docs/PROJECT_AUDIT.md`：项目现状、运行结果、代码与文档差异。
-   `docs/PROJECT_PLAN.md`：里程碑、依赖、优先级与任务状态。
-   `docs/KNOWN_ISSUES.md`：风险、复现步骤、影响和处理建议。
-   经核实的 API 与数据库待办清单。

## 6. 验收标准

-   [ ] 能明确说明项目如何构建、如何启动、依赖哪些服务。
-   [ ] 每个已有模块都有基于代码或测试证据的状态判断。
-   [ ] API 文档和真实实现的主要差异已登记。
-   [ ] 敏感配置得到检查，不在报告或仓库中暴露真实凭证。
-   [ ] 首版产品范围明确：个人内容展示优先，社区功能暂缓。
-   [ ] 未经审计，不进行大范围重写或无理由升级依赖。

## 7. 风险与决策

-   若无法在当前环境启动，记录限制和证据，不直接认定代码不可用。
-   若接口文档与代码冲突，先登记并协调，不默默按猜测改写。
-   若现有认证模块复杂且首版只需站长管理，评估最小化方案，但必须保留必要的管理端安全保护。

## 8. 阶段完成定义

审计报告经过确认，首版范围和后续任务顺序明确，能够进入阶段
1。此阶段不要求把所有已知问题全部修复。
