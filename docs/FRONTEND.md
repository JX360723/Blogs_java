# 前端项目规范与容器化部署约定

> 项目：Knowledge Blog（`blogs`）\
> 文档用途：作为前端开发、AI
> 辅助编码、联调、容器化部署与验收的统一约束。\
> 当前阶段：前端尚未开始；后端已有部分实现，需在审计后与本规范联调。\
> 核心原则：先在本地完整运行并验收，再部署到服务器；优先适配 2 vCPU / 8
> GiB，资源不足时可升级至 4 vCPU / 8 GiB。

------------------------------------------------------------------------

## 1. 项目目标

建设一个可维护、可测试、可容器化部署的知识分享博客前端，至少覆盖：

-   博客公开页面：首页、文章列表、文章详情、分类/标签筛选。
-   用户功能：注册、登录、当前用户信息、退出登录。
-   管理功能：文章管理、文章编辑与发布、分类管理、标签管理。
-   AI 问答：在后端接口实现并确认协议后，支持流式回答和历史会话。
-   工程交付：本地可重复启动、前后端可联调、Docker
    部署可复现、具备基本运行与排错文档。

本规范不代表上述功能已经实现。所有功能均需经过开发和验收后才能标记为完成。

## 2. 技术栈（确定项）

--------------------------------------------------------------------------------------------------------
  层面                    选型                    约定
----------------------- ----------------------- --------------------------------------------------------
  前端框架                Vue 3                   使用 Composition API，优先采用 `<script setup>`

  语言                		JavaScript              开启严格类型检查；避免无必要的 `any`

  构建工具                Vite                    开发服务器、构建与环境变量管理

  UI 组件库               Element Plus            统一后台表单、表格、弹窗、分页和反馈组件

  路由                    Vue Router              页面路由、路由元信息、登录与角色访问控制

  状态管理                Pinia                   管理登录用户、认证状态及确有必要的共享状态

  HTTP 客户端             Axios                   统一 API 基址、超时、请求头、错误处理和响应解析

  容器化                  Docker                  前端使用多阶段构建，运行阶段使用轻量 Web 服务器

  编排                    Docker Compose          本地统一启动前端、后端及所需依赖；生产部署沿用可维护的
                                                  Compose 配置
  --------------------------------------------------------------------------------------------------------

如后续因代码审计发现已有技术选型或版本约束，应先记录差异并评估迁移成本，不得未经确认擅自替换以上确定项。

## 4. 页面与功能范围

### 4.1 博客公开页面

-   首页：展示最新文章或约定的内容入口。
-   文章列表：分页，支持后端实际提供的分类、标签、关键词筛选。
-   文章详情：标题、摘要、正文、分类、标签、发布时间等，以后端实际字段为准。
-   分类/标签入口：展示已启用分类与可用标签。
-   登录与注册页面。
-   加载中、空状态、请求失败、无权限和页面不存在等状态。

### 4.2 管理页面

-   管理后台布局与导航。
-   文章列表及状态筛选。
-   新建、编辑、预览、保存草稿、发布和删除操作；仅实现后端已支持并确认的状态流转。
-   分类管理。
-   标签管理；若后端接口尚未具备，先登记为前后端联动任务，不得用本地假数据冒充已完成。
-   管理权限校验及无权限提示。

### 4.3 AI 问答（条件性交付）

在后端确认 AI API 的请求方法、鉴权方式、SSE
事件格式、错误格式和会话接口后实施。前端至少处理：

-   流式内容增量展示。
-   加载中、完成、失败、用户停止或连接中断。
-   会话列表及历史消息（以后端实际接口为准）。
-   重连策略和重复消息风险。
-   限流、未登录、权限不足等错误。

不要在 API 契约未确认时自行猜测字段或事件名。

## 5. 前端编码约定

### 5.1 Vue 与 TypeScript

-   使用 Vue 3 Composition API 与 `<script setup lang="ts">`。
-   Props、事件、表单模型、API 请求和响应定义明确的 TypeScript 类型。
-   不将业务逻辑全部塞入页面组件；可复用逻辑抽入 composables、API
    模块或业务组件。
-   不在模板中堆叠复杂条件；复杂逻辑在脚本中命名并测试。
-   组件命名、文件命名保持项目内一致；一个组件尽量聚焦一个职责。

### 5.2 API 请求封装

-   所有后端请求统一经 Axios 实例及 `src/api/` 模块调用。
-   API 基址从环境变量读取，不在业务组件中硬编码主机、端口或域名。
-   统一处理超时、网络错误、401、403、404、429 和 5xx。
-   不将 HTTP 状态码与业务响应码混为一谈。
-   对返回类型进行显式声明；避免在每个页面重复解析响应包装。
-   Token 不得写入日志、错误提示或提交到代码仓库。
-   请求失败时给出用户可理解的反馈，并保留必要的诊断信息。

后端现有规范使用 `Result<T>` 包装普通 HTTP 响应，字段包括
`code`、`message`、`data`、`timestamp`。实现时必须核对后端实际返回值，统一响应解析规则；SSE
不应强行套用普通 JSON 响应处理。

### 5.3 环境变量

建议提供 `.env.example`，仅包含非敏感示例：

``` dotenv
# 本地开发时的 API 地址；应与后端实际端口保持一致
VITE_API_BASE_URL=/api/v1
```

约定：

-   `VITE_` 前缀变量会被打包进浏览器代码，**不得存放密钥、密码、私有
    Token 或其他秘密信息**。
-   本地开发可使用 Vite 代理将 `/api` 转发到后端。
-   容器部署优先让浏览器访问同源路径 `/api`，由 Nginx
    反向代理至后端服务，减少跨域配置复杂度。
-   若采用相对路径，Axios 的 `baseURL`、Vite 代理和 Nginx 路由必须一致。
-   前端构建时注入的环境变量是构建期配置。若要求同一镜像在不同环境间复用，应设计运行时配置方案，不能假设修改容器环境变量就会自动改变已打包的静态文件。

### 5.4 路由与权限

-   使用 Vue Router 的路由元信息标记是否需要登录及所需角色。
-   Pinia 负责维护前端登录状态；路由守卫用于用户体验层面的导航控制。
-   **前端路由隐藏不等于安全授权**。所有真实权限必须由后端 Spring
    Security 等机制校验。
-   未登录访问受保护页面时引导至登录页，并在登录后按安全规则返回原页面。
-   退出登录时清除客户端认证状态及相关缓存。
-   不允许仅凭前端传入的角色字段授予权限。

### 5.5 Markdown 与内容安全

-   文章正文按后端实际约定处理 Markdown 或 HTML。
-   不直接把未经清洗的 HTML 注入 DOM。
-   如需渲染
    HTML，必须采用经过审查的清洗策略，并验证脚本、事件属性和危险 URL 等
    XSS 风险。
-   编辑器预览与最终文章详情应尽量保持一致。

### 5.6 质量与可访问性

-   所有表单具有校验和清晰的错误提示。
-   按钮在请求处理中应防止重复提交。
-   列表具备加载、空数据、错误和分页状态。
-   关键操作（删除、发布等）应有适当确认。
-   兼顾常见桌面浏览器与窄屏布局。
-   不提交调试代码、无用依赖、假数据或硬编码凭证。

## 6. 与后端 API 的协作规则

后端当前规划的基准路径为 `/api/v1`，普通响应采用统一 `Result<T>`
结构。前端开发前必须对照实际后端确认：

-   注册、登录、当前用户信息的请求与响应字段。
-   Token 的传递方式及失效处理。
-   文章列表分页字段、筛选参数和文章状态枚举。
-   分类树与标签接口的数据结构。
-   文章创建、更新、逻辑删除的权限与响应。
-   Markdown/HTML 字段的用途。
-   AI SSE 请求方式、事件协议、错误与结束标记。

接口缺失或规范冲突时，先更新 API
契约并与后端实现同步，再编写依赖该接口的前端功能。不要以临时 mock
数据代替真实联调验收；开发阶段可以使用
mock，但必须显式标识并在真实联调时移除或隔离。

## 7. 容器化架构

### 7.1 目标架构

``` text
Browser
   |
   v
Frontend Nginx container
   |-- /          -> Vue static files
   |-- /api/      -> Backend service
   |
   v
Spring Boot backend container
   |-- MySQL 8.0
   |-- Redis (if required by the backend)
   |-- AI provider (external service, if enabled)
```

建议生产环境由反向代理统一对外暴露入口。数据库和 Redis
默认不向公网开放，仅在 Docker
内部网络或受控网络中供应用访问。若已有统一入口代理，应避免重复部署多个互相冲突的代理层。

### 7.2 前端镜像

-   使用多阶段 Docker 构建：Node.js 阶段安装依赖并构建，Nginx
    阶段仅提供静态文件。
-   使用锁文件进行可复现安装，例如 `npm ci`。
-   Nginx 必须配置 Vue Router history 模式的 SPA fallback。
-   配置 `/api/` 反向代理到 Compose 内部的后端服务名及端口。
-   静态资源启用合理缓存；入口 HTML 不应设置导致版本更新失效的长期缓存。
-   不把 Node.js 开发服务器用作生产静态站点服务器。
-   容器尽量以非 root
    用户运行（基于镜像与端口配置可行时），使用小型基础镜像并定期更新。

### 7.3 Docker Compose 服务

根据后端实际情况，至少评估以下服务：

-   `frontend`：构建后的 Vue 静态站点与 Nginx。
-   `backend`：Spring Boot 应用。
-   `mysql`：MySQL 8.0，使用持久化卷。
-   `redis`：仅在后端确实依赖 Redis 时启用，并配置访问控制。
-   可选的数据库迁移/初始化任务。

要求：

-   使用 Compose 内部 DNS 服务名访问其他容器，不能在容器内使用
    `localhost` 访问另一个容器。
-   数据库密码、JWT 密钥、AI API Key
    等通过本地未提交的环境文件或部署密钥注入。
-   提供 `.env.example`，不得提交真实 `.env`。
-   数据库使用持久化卷，明确备份与恢复步骤。
-   服务配置合理的重启策略和健康检查；应用启动顺序不能只依赖
    `depends_on`，还应确认依赖服务健康。
-   生产环境避免将 MySQL、Redis 管理端口直接暴露到公网。
-   镜像标签尽量固定版本，不在正式环境中无控制地使用 `latest`。
-   生产部署需有日志查看、升级、回滚和数据备份方案。

### 7.4 网络与代理

-   本地开发可通过 Vite proxy 转发 API。
-   容器化部署由 Nginx 代理 `/api/` 到后端服务。
-   后端服务名、容器端口、API
    前缀和尾部斜杠行为必须统一测试，避免路径重复或丢失。
-   后端若使用
    SSE，代理需关闭该路由的响应缓冲，并配置适当的读取超时；否则可能出现内容批量到达而非实时输出。
-   需要正确转发 `Host`、客户端 IP
    和协议头，并由后端安全地信任配置的代理信息。

## 8. 服务器资源目标与容量控制

### 8.1 基准环境

目标服务器：**2 vCPU / 8 GiB RAM**。如果经过实测发现 CPU
或内存压力持续过高，可以升级至 **4 vCPU / 8 GiB RAM**。

2 vCPU / 8 GiB 应作为首要优化目标，而不是默认要求必须升级。4 vCPU
能改善并行处理能力，但不会增加内存总量，因此不能仅靠升级 CPU
解决内存不足。

### 8.2 资源管理原则

-   先在本地完整验证，再在目标规格服务器进行压力与资源测试。
-   先测量，再决定容器资源限制；不要凭空给出看似精确的 CPU、内存配额。
-   关注主机内存、容器 RSS、CPU
    利用率、GC、请求延迟、错误率、磁盘和数据库连接数。
-   MySQL、Redis、Spring Boot 和 Nginx
    的资源必须整体核算，不能只评估前端容器。
-   为操作系统、Docker、日志、备份和突发负载保留内存余量。
-   避免过度配置 Java 堆；根据实际负载设置 JVM 内存上限并观察 GC。
-   对 MySQL 缓冲池、连接池、Redis 最大内存与淘汰策略进行按负载配置。
-   生产环境设置日志轮转，避免容器日志耗尽磁盘。
-   对 AI
    请求设置超时、限流和并发限制，避免外部服务变慢时持续占用本地连接与线程。
-   若资源紧张，优先检查内存泄漏、重复服务、数据库配置和并发峰值，再评估升级
    CPU；若是内存瓶颈，需减少内存占用或增加 RAM。

### 8.3 最低运行验证

在目标服务器上至少完成：

1.  全部容器健康状态正常。
2.  前端首页和静态资源可访问。
3.  登录、文章列表、文章详情、文章发布等核心链路可用。
4.  前端通过反向代理访问后端，无错误的跨域或 API 路径。
5.  后端所需的 MySQL、Redis 可连接，重启容器后数据仍在。
6.  SSE（如纳入首版）能逐步收到消息，并能正常结束。
7.  观察代表性负载下 CPU、内存、GC、响应时间和错误率。
8.  完成数据库备份与恢复演练。

## 9. 本地开发与部署流程

### 9.1 本地前端开发

前提：安装与项目要求兼容的 Node.js LTS 版本和 npm。

``` bash
cd frontend
npm ci
npm run dev
```

在项目创建时应确保 `package.json`
至少提供适当的开发、构建和类型检查脚本。脚本名称以实际工程为准，不能假定尚未创建的工程已经具备这些命令。

### 9.2 前端构建检查

``` bash
npm ci
npm run build
```

如果工程配置了单独的类型检查脚本，也必须执行该脚本。构建成功并不自动代表类型检查、业务测试和浏览器运行全部通过。

### 9.3 容器启动

在仓库根目录按项目提供的 Compose
文件启动。示例命令需在文件创建并核对服务名称后使用：

``` bash
docker compose config
docker compose build
docker compose up -d
docker compose ps
docker compose logs -f
```

验收时应逐个确认服务状态、健康检查、前端入口、API
代理、数据库连接和核心业务链路。停止服务可使用：

``` bash
docker compose down
```

普通停止不应删除持久化卷。只有明确理解数据影响并做好备份后，才可使用会删除卷的命令。

### 9.4 本地验收顺序

1.  安装依赖、类型检查和前端构建。
2.  后端独立启动并验证健康状态。
3.  数据库初始化、迁移和连接验证。
4.  前后端本地联调。
5.  使用 Docker Compose 从干净环境启动全套服务。
6.  验证核心功能、错误场景和容器重启后的数据持久性。
7.  整理复现步骤和测试结果，再部署到服务器。

## 10. 测试与验收标准

### 10.1 前端工程验收

-   [ ] 依赖可通过锁文件稳定安装。
-   [ ] TypeScript 检查通过。
-   [ ] 生产构建成功。
-   [ ] 路由刷新后不出现 SPA 404。
-   [ ] API 基址与代理配置一致。
-   [ ] 401、403、404、429、5xx 和网络断开有可理解的处理。
-   [ ] 登录态恢复、失效与退出流程正确。
-   [ ] 页面具备加载、空、失败和无权限状态。
-   [ ] 不存在已知的高风险 HTML 注入问题。

### 10.2 业务验收

-   [ ] 用户可注册、登录并获取当前用户信息。
-   [ ] 公开用户可以查看允许公开的文章。
-   [ ] 未登录用户无法执行需要认证的操作。
-   [ ] 普通用户不能执行管理员操作。
-   [ ] 文章作者和管理员权限符合后端规则。
-   [ ] 文章列表分页、筛选、详情与状态展示正确。
-   [ ] 分类、标签与文章关联行为符合接口契约。
-   [ ] AI
    功能若纳入版本范围，流式输出、错误、结束和历史会话均通过验证。

### 10.3 容器与部署验收

-   [ ] Docker 镜像可从项目源码重新构建。
-   [ ] Compose 配置检查通过。
-   [ ] 容器之间使用正确的内部服务名通信。
-   [ ] 关键服务健康检查正常。
-   [ ] 数据库数据在容器重建后仍然保留。
-   [ ] 敏感配置未提交到仓库或前端静态资源。

## 11. AI 辅助开发工作规则

AI 编码工具在本项目中必须遵守：

1.  开始任务前先阅读本文件、`CLAUDE.md`、`API_SPEC.md` 和相关代码。
2.  先说明将修改的文件、原因、依赖和验收方法；小型、明确的修复可直接执行。
3.  不随意升级依赖、不替换已确定的技术栈、不重写无关模块。
4.  不编造后端接口，不将 mock 数据描述为真实功能。
5.  不写入真实密钥，不把敏感信息暴露给浏览器。
6.  完成后运行可用的检查和测试，并明确区分"已验证"与"尚未验证"。
7.  若发现接口文档与后端实现冲突，记录差异并提出协调方案。
8.  一次优先完成一个可独立验收的任务，避免大范围、难回滚的修改。

建议每个任务记录：编号、目标、修改范围、前置依赖、验收标准、测试命令、测试结果、遗留问题和状态。
